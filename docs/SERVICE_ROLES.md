# Роли сервиса и назначение владельца

Роли сервиса не связаны с ролями участников отдельных чатов и досок.

| Роль | Доступ |
|---|---|
| OWNER — владелец | Все разделы, назначение ролей |
| ADMIN — администратор | Настройки, SMTP, LiveKit/TURN, балансы и управление пользователями; без назначения ролей |
| MODERATOR — модератор | Обзор, пользователи, блокировки обычных аккаунтов, жалобы, поддержка, журнал |
| MANAGER — менеджер | Обзор, пользователи, блокировки обычных аккаунтов, жалобы, поддержка, журнал |
| ANALYST — аналитик | Обзор и агрегированная статистика, только чтение |
| BOARD — совет директоров | Обзор, агрегированная статистика и журнал, только чтение |
| USER — пользователь | Без доступа к панели |

Менеджер не меняет имена, пароли, роли, балансы, подписки и настройки сервера.
Аналитик не получает список пользователей и содержимое обращений. Совет директоров
видит имена участников и подробности событий журнала, но не открывает карточки
пользователей и не архивирует журнал. Очистка журнала для OWNER, ADMIN, MODERATOR
и MANAGER переносит записи в архив, сохраняя исходники. Последнего владельца
нельзя лишить роли через панель. Проверки выполняются сервером при каждом запросе.

## Команда оператора при установке

Сначала запустите сервер с миграциями, зарегистрируйте нужный аккаунт и подтвердите
email. Затем выполните команду на сервере (из каталога проекта):

```sh
docker compose --env-file .env -f infrastructure/docker/docker-compose.yml exec backend /opt/mango/bin/app --bootstrap-owner andrk774
```

Для Kubernetes (подставьте свой контекст и namespace):

```sh
kubectl --context docker-desktop -n mango-dev exec deployment/backend -- /opt/mango/bin/app --bootstrap-owner andrk774
```

Для установки без контейнера:

```sh
./backend/app/build/install/app/bin/app --bootstrap-owner andrk774
```

В Windows используйте `app.bat` вместо `app`. Переменные подключения к базе должны
быть теми же, что у установленного сервера. Пароли не передаются аргументами команды.

Команда разрешает несколько владельцев: существующие OWNER сохраняют доступ.
Повторное назначение уже действующего OWNER безопасно и не создаёт лишних событий.
Несуществующий, заблокированный, удалённый или не подтвердивший email аккаунт
получит отказ. Изменение роли и событие `OWNER_BOOTSTRAP` сохраняются одной
транзакцией. В журнале явно указано, что назначение выполнено серверным оператором;
actor указывает целевой аккаунт. Пароли, ключи и пользовательские данные не меняются.

Команда не запускает HTTP-сервер и не выполняет миграции. Код выхода: 0 — успех
(включая уже назначенного владельца), 1 — отказ/ошибка, 2 — неправильные аргументы.
`--help` показывает справку без подключения к БД. Это серверная операция: доступ
к Docker exec / Kubernetes exec / окружению backend должен быть только у операторов.
После назначения обновите страницу панели или откройте её заново в приложении.
