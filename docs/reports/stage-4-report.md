## 2. Что сделано на сервере

### 2.1. Модуль `sync` — журнал событий

Источник истины для синхронизации. WebSocket лишь ускоряет доставку
того, что уже записано сюда.

- Запись события и изменение данных фиксируются **одной транзакцией**.
  Иначе возможны два испорченных состояния: сообщение есть, а события
  нет, либо наоборот.
- Выбран fan-out на запись — строка на получателя
  ([ADR-0015](../adr/0015-event-fanout-on-write.md)). У клиента ровно
  один курсор, догонка — это `WHERE user_id = ? AND id > ?`.
- Устаревший курсор даёт `410 Gone` со списком областей для перезагрузки:
  клиент перезагружает **только их**, а не всю базу.

### 2.2. Модуль `messaging` — чаты и сообщения

| Возможность | Решение |
|---|---|
| Порядок сообщений | Счётчик в строке чата, `SELECT ... FOR UPDATE` сериализует отправки ([ADR-0016](../adr/0016-message-ordering-and-idempotency.md)) |
| Идемпотентность | Уникальный индекс `(chat, sender, clientMsgId)`; повтор возвращает `200` с тем же сообщением |
| Личный чат | Нормализованный ключ пары участников — второй такой чат невозможен |
| Защита от IDOR | Условие участия в чате в каждом запросе; ответ для чужого и несуществующего чата одинаков |
| Список чатов | Один запрос с LATERAL вместо N+1 |
| Пагинация | По номеру сообщения, без `OFFSET` |
| Удаление | Мягкое: текст стирается, номер остаётся занятым |

### 2.3. Модуль `realtime` — доставка в реальном времени

- WebSocket с аутентификацией **первым кадром**, а не параметром адреса:
  адрес попадает в журналы прокси, и убрать токен оттуда уже невозможно.
- Рассылка между экземплярами через Redis pub/sub; подписка по требованию
  — только на каналы подключённых пользователей.
- Очередь исходящих на соединение ограничена: при переполнении соединение
  разрывается, клиент переподключается и догоняет по курсору. Безразмерная
  очередь при медленном клиенте съела бы память сервера.
- Потеря рассылки не теряет событие — оно уже в журнале.

### 2.4. Список отозванных сессий

Сквозная проверка живого стека вскрыла пробел: **отзыв сессии не прекращал
действие уже выданного access token**. Подписанный JWT проверяется без
обращения к базе, поэтому после обнаружения кражи у злоумышленника
оставалось до пятнадцати минут доступа — ровно в тот момент, когда дорога
каждая минута.

Исправлено ([ADR-0017](../adr/0017-session-revocation-list.md)): при
закрытии сессии её идентификатор попадает в список на время жизни токена,
и проверка отвергает такие токены. Работает при выходе, смене пароля,
отзыве сессии владельцем и обнаружении кражи.

## 3. Что сделано на клиенте

### 3.1. Новые модули

| Модуль | Содержимое |
|---|---|
| `:core:network` | Retrofit, DTO, прозрачное обновление токена, перевод HTTP-ошибок в доменные |
| `:core:sync` | Процессор очереди исходящих, применение событий, фоновая задача |
| `:core:realtime` | WebSocket с переподключением, сверкой по курсору и поиском разрывов |

### 3.2. Очередь исходящих заработала

Очередь была спроектирована и покрыта тестами ещё на Этапе 2 — не хватало
только транспорта. Теперь операции уезжают:

- повтор при неизвестном исходе безопасен: ключ идемпотентности
  обеспечивает возврат того же сообщения вместо создания второго;
- отказ `4xx` помечает сообщение как неотправленное — повтор не изменит
  исход, решение за пользователем;
- `5xx` и сетевые ошибки откладывают попытку с нарастающей задержкой;
- операции, которые сервер пока не принимает (задачи — Этап 5),
  **не блокируют очередь**: выборка фильтруется по типу операции.

### 3.3. Применение событий — в одном месте

События приходят двумя путями: через сокет и через догонку по курсору.
Применяет их один и тот же код, иначе состояние базы зависело бы от того,
каким каналом пришло изменение.

Собственное отправленное сообщение сопоставляется с локальной строкой
по клиентскому идентификатору — иначе оно появилось бы в переписке дважды.

### 3.4. Экраны

- Вход, регистрация и подтверждение адреса.
- Переписка: список сообщений, композер, догрузка истории при прокрутке,
  отметка о прочтении, повтор неотправленного.
- Список чатов: обновление с сервера, поиск людей, создание переписки.

Поле ввода очищается **сразу**, не дожидаясь ответа сервера: сообщение
уже сохранено локально. При отказе текст возвращается в поле — пропажа
набранного недопустима.

## 4. Дефекты, найденные собственными проверками

| Что нашло | Дефект | Почему это важно |
|---|---|---|
| Сквозная проверка стека | Отзыв сессии не прекращал действие выданного access token | Обнаружение кражи токена срабатывало с задержкой в четверть часа |
| Интеграционный тест | `readOnly` снимал флаг read-only, не завершив транзакцию | **Любой отказ в доступе на чтении превращался в 500.** Тест «чужой и несуществующий чат отвечают одинаково» это пропускал: оба ответа были одинаково неверными |
| Android Lint | WorkManager инициализировался дважды | Фоновая синхронизация могла молча не заработать: первым поднимался экземпляр без фабрики воркеров |
| Сборка образа | Dockerfile перечислял модули поимённо | Новые модули не попадали в образ, и контейнер молча запускал устаревший код |
| Компилятор Kotlin | Dagger не видит значения параметров по умолчанию | Граф зависимостей не собирался |

Отдельно: тест на одновременную отправку двенадцати сообщений подтвердил,
что блокировка строки чата действительно сериализует выдачу номеров —
без неё часть запросов отваливалась бы на уникальном индексе.

## 5. Незакрытые проверки

| Проверка | Причина |
|---|---|
| **Приложение ни разу не запускалось** | Нет эмулятора и устройства. APK собирается, но не установлен |
| Соответствие клиентских DTO ответам сервера | Проверяется только вручную написанными образцами. Автоматической сверки нет — см. ниже |
| WebSocket со стороны клиента | Протокол покрыт тестами разбора; само соединение проверено только серверными тестами |
| Поведение при обрыве связи на реальном устройстве | Требует устройства |
| Нагрузка, производительность | Измерений не проводилось |

### Разрыв в проверке контракта

Серверные DTO и клиентские описаны раздельно и сверяются вручную.
Контрактный тест проверяет, что заявленные в OpenAPI эндпоинты
отвечают, но **не** что формат тела совпадает с ожиданиями клиента.

Расхождение проявилось бы как ошибка разбора в приложении, а не при
сборке. Варианты закрытия (решение отложено до Этапа 7): генерация
клиентских DTO из OpenAPI либо общий тест, прогоняющий записанные
ответы сервера через клиентский разбор.

## 6. Ограничения, зафиксированные сознательно

| Ограничение | Причина |
|---|---|
| Усиление записи журнала: строка на участника | Выбор в пользу простой догонки; для крупных групп потребует пересмотра |
| Отправки в один чат сериализуются | Цена гарантии порядка; разные чаты идут параллельно |
| Недоступность Redis ослабляет отзыв сессий | Отказ всем из-за сбоя хранилища хуже временного окна |
| Черновики не синхронизируются | Серверного хранения нет; операция выполняется локально |
| Реакции и пересылка не реализованы | Этап 6 |
| Сквозная проверка использует только ASCII | Git Bash на Windows портит кодировку кириллицы в аргументах curl. Обработка кириллицы проверяется тестами на JVM |

- Что приложение работает на устройстве. Оно **ни разу не запускалось**:
  проверены сборка, модульные и интеграционные тесты, серверная часть
  на живом стеке.
- Что клиент и сервер договорились о формате данных. Это проверено
  вручную написанными образцами, а не автоматической сверкой.
- Что производительность приемлема. Измерений не было.
- Что безопасность проверена. Сделана самопроверка по чек-листу;
  внешнего аудита не было.
