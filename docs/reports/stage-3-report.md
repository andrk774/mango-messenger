## 2. Что сделано

### 2.1. Схема данных

Миграция `V001__init.sql` — 16 таблиц, 34 индекса. Применяется Flyway
при старте приложения, до приёма трафика.

Инварианты заданы схемой, а не только кодом:

| Ограничение | Что защищает |
|---|---|
| `UNIQUE (conversation_id, sender_id, client_msg_id)` | дубликат сообщения при повторной отправке |
| `UNIQUE (conversation_id, seq)` | однозначный порядок внутри чата |
| `UNIQUE (user_id, client_op_id)` в `outbox_operations` | повторное применение операции |
| `UNIQUE (direct_key) WHERE type = 'DIRECT'` | второй личный чат между теми же людьми |
| `UNIQUE (refresh_token_hash)` | коллизия токенов обновления |
| `UNIQUE (push_provider, push_token)` | уведомление не тому устройству после переустановки |
| `CHECK` на `type`, `status`, `priority`, `role` | недопустимое значение при ошибке в коде |

Уникальность email и username действует только среди живых учётных
записей (`WHERE deleted_at IS NULL`): удалённый пользователь не должен
вечно удерживать адрес.

### 2.2. Аутентификация

Реализовано и проверено тестами:

- **Регистрация** с подтверждением адреса по письму.
- **Вход** с выдачей пары токенов и записью устройства.
- **Обновление** access token с ротацией refresh.
- **Выход**, список активных сессий, отзыв конкретной сессии.
- **Восстановление пароля** с отзывом всех сессий.
- **Профиль** текущего пользователя.

Решения по безопасности вынесены в ADR:

| Решение | ADR |
|---|---|
| Argon2id на Bouncy Castle, параметры внутри хеша | [0012](../adr/0012-argon2id-bouncycastle.md) |
| Ротация refresh и реакция на повторное использование | [0013](../adr/0013-refresh-rotation-and-reuse-detection.md) |
| Эндпоинты не раскрывают, зарегистрирован ли адрес | [0014](../adr/0014-no-account-enumeration.md) |
| Прямой SQL без ORM | [0011](../adr/0011-sql-without-orm.md) |

### 2.3. Ограничение частоты запросов

| Операция | Предел | Ключ |
|---|---|---|
| Вход | 5 за 15 минут | адрес почты + адрес клиента |
| Регистрация | 3 за час | адрес клиента |
| Восстановление пароля | 3 за час | адрес почты |

Ключ входа включает **и** адрес почты, **и** адрес клиента. Только адрес
клиента позволил бы перебирать пароль к одному аккаунту с меняющихся
адресов; только адрес почты позволил бы одному клиенту за NAT
заблокировать вход всем остальным.

**Ограничение реализации:** счётчики хранятся в памяти процесса. При
нескольких экземплярах приложения фактический предел умножается на их
число. Перенос счётчиков в Redis запланирован на Этап 4, когда Redis
будет задействован для рассылки событий.

### 2.4. Инфраструктура

`docker compose up` поднимает PostgreSQL 17, Redis 7.4, Mailpit и backend.

- Порты на хосте нестандартные (5433, 6380, 8026, 8081): на машине
  разработчика уже может работать другой проект, и занятый порт —
  самая частая причина «не запускается».
- Все порты публикуются **только на 127.0.0.1**: база не должна быть
  видна из локальной сети.
- `depends_on` ждёт именно **готовности** (`service_healthy`), а не
  запуска: иначе миграции стартуют раньше, чем PostgreSQL примет
  подключение.
- Образ многоэтапный, процесс работает **не от root**.
- `MaxRAMPercentage` вместо `-Xmx`: JVM учитывает лимит памяти
  контейнера, а не память хоста.

### 2.5. Эксплуатационные свойства

- **Проверки живости и готовности разделены.** `/v1/health` не зависит
  от внешних систем: кратковременная недоступность базы не повод
  перезапускать процесс. `/v1/health/ready` проверяет базу — по ней
  балансировщик решает, слать ли запросы.
- **Корректная остановка:** Netty дорабатывает принятые запросы, затем
  закрывается пул соединений.
- **Идентификатор запроса** (`X-Request-Id`) проходит через журнал и
  возвращается в теле ошибки как `traceId`.
- **Персональные данные редактируются** перед записью в журнал.
- Ошибка превращается в HTTP-ответ в **одном месте** — ни один
  обработчик не может вернуть 200 при отказе.

## 3. Дефекты, найденные собственными проверками

Раздел приведён потому, что показывает: проверки работают, а не
создают видимость.

| Что нашло | Дефект | Почему это важно |
|---|---|---|
| Интеграционный тест | Отзыв всех сессий при обнаружении кражи refresh выполнялся **внутри транзакции**, которую тут же откатывало выбрасываемое исключение | Защита от кражи токена не срабатывала вовсе — ровно в том сценарии, ради которого написана |
| Интеграционный тест | Нечисловое значение `X-Forwarded-For` роняло вход с кодом 500 при записи в колонку `inet` | Заголовок управляется клиентом: одним запросом можно было сломать аутентификацию |
| Собственный разбор кода | Перехват нарушения уникальности внутри транзакции с последующим `commit` | В PostgreSQL ошибка ограничения **прерывает транзакцию**; код был обречён падать на фиксации. Заменено на `ON CONFLICT DO NOTHING RETURNING` |
| Модульный тест | Проверка срока действия JWT идёт по системным часам: java-jwt 4.6 не позволяет подменить источник времени | Тест на истечение срока, построенный на сдвиге поддельных часов, проверял бы не то, что кажется |

## 4. Расхождения с исходным планом

### 4.1. MinIO исключён из стека

Образы MinIO перестали быть доступны для анонимной загрузки: Docker Hub
отдаёт 404 на репозиторий `minio/minio`, quay.io требует аутентификации
(проверено 12.11.2026; анонимная загрузка с Hub в целом работает —
`hello-world` скачивается).

Объектное хранилище нужно для вложений, то есть на Этапе 6. Добавлять
в стек заведомо нерабочий сервис ради функции, которой ещё нет, означало
бы ломать запуск у всех. Сервис убран с объяснением в самом
`docker-compose.yml`; выбор провайдера (SeaweedFS, Zenko CloudServer либо
MinIO с учётной записью) делается на Этапе 6.

### 4.2. OpenAPI приведён в соответствие с реализацией

Черновик Этапа 1 описывал ответ `409` на занятый адрес при регистрации.
Это противоречит [ADR-0014](../adr/0014-no-account-enumeration.md):
код состояния раскрывал бы наличие учётной записи независимо от того,
выровнено ли время ответа. Спецификация исправлена на `202`.

Реализованные операции помечены в спецификации флагом
`x-implemented: true`, и **контрактный тест проверяет**, что каждая
такая операция действительно отвечает на сервере. Остальные описаны
как контракт будущих этапов и намеренно ещё не реализованы.

## 6. Что дальше

### Этап 4 — Messenger MVP

Серверная часть:

- модуль `messaging`: чаты, участники, сообщения с выдачей `seq`;
- модуль `sync`: журнал событий, курсоры, серверная идемпотентность
  по `Idempotency-Key`;
- модуль `realtime`: WebSocket-хаб, рассылка через Redis pub/sub;
- перенос счётчиков ограничения частоты в Redis.

Клиентская часть:

- модули `:core:network`, `:core:sync`, `:core:realtime`;
- процессор очереди исходящих операций — он уже спроектирован и покрыт
  тестами, не хватает только транспорта;
- экраны входа и переписки.

### Технический долг

1. Счётчики ограничения частоты — в Redis.
2. Фоновая очистка: отозванные сессии, использованные токены из писем,
   записи идемпотентности старше 7 дней.
3. Выбор S3-совместимого хранилища.
4. Миграция Android на AGP 9.1 + compileSdk 37 (из Этапа 2).
   **Блокер частично снят:** `cmdline-tools` в SDK уже установлены
   (появились вместе с `scripts/sdk.sh` после отчёта по Этапам 1–2),
   то есть `sdkmanager` доступен. Осталось установить платформу
   `android-37` и принять лицензии — это решение владельца окружения,
   а не техническое препятствие. Сама миграция затронет все модули
   и требует отдельной проверки сборкой, поэтому в Этап 3 не включена.

## 7. Чего этот отчёт не утверждает

- Что backend готов к продакшну. Нет TLS, нет наблюдаемости за пределами
  журналов, нет нагрузочных испытаний.
- Что обмен сообщениями работает. Реализована только аутентификация.
- Что безопасность проверена. Сделана самопроверка по чек-листу;
  внешнего аудита не было.
- Что ограничение частоты защитит установку из нескольких экземпляров.
  Счётчики локальны для процесса, и это указано явно.
