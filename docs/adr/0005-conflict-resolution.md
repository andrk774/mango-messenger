# ADR-0005: Разрешение конфликтов — per-field LWW для задач, поэлементное слияние исполнителей

- **Статус:** принято
- **Дата:** 2026-11-12 (уточнено 2026-11-13, этап 5)
- **Этап:** 1

## Контекст

Сообщения по своей природе append-only: их почти не редактируют, и конфликтов
практически не возникает. Задачи — изменяемые объекты, которые правят с
нескольких устройств и несколько человек одновременно. Нужна политика,
понятная пользователю и не теряющая данные молча.

Простая блокировка по версии всего объекта (отклонять PATCH при расхождении)
на практике означает: один человек поменял срок, другой в это же время —
приоритет, и второй получает ошибку, хотя конфликта по сути нет.

## Решение

| Поле | Стратегия | Обоснование |
|---|---|---|
| `title`, `description` | LWW по полю | Текст редко правят одновременно |
| `status` | LWW по полю; при равных метках времени выигрывает больший `conflictWeight` (DONE > CANCELLED > REVIEW > IN_PROGRESS > TODO) | Завершение — более сильное намерение, чем возврат в работу |
| `priority`, `due_at` | LWW по полю | — |
| `assignees` | **Поэлементное слияние**: add и remove по разным людям применяются независимо; для одного человека побеждает операция, пришедшая на сервер позже | Два человека назначили разных исполнителей — остаются оба; см. «Уточнение этапа 5» |
| `comments`, `attachments` | append-only, дедуп по `client_op_id` | Конфликтов нет по построению |
| `subtasks` | append-only + LWW по каждой подзадаче | — |

Механика: клиент отправляет `PATCH /tasks/{id}` с `baseVersion` и **только
изменёнными полями** плюс метки времени изменения по каждому полю. Сервер:

1. `baseVersion == version` → применяет, `version++`;
2. `baseVersion < version` → применяет per-field LWW, возвращает `200`
   с итоговым объектом и списком `conflicts`;
3. клиент принимает серверный объект как истину и, если его правка
   проиграла, показывает ненавязчивое уведомление.

Каждое изменение пишется в `task_events`. Это ключевая страховка: даже
проигравшая правка остаётся в истории, и конфликт можно разобрать постфактум.

## Альтернативы

- **Блокировка по версии всего объекта.** Отклонено: ложные конфликты при
  правках разных полей.
- **Последняя запись побеждает целиком (object-level LWW).** Отклонено:
  молча теряет параллельные изменения других полей.
- **CRDT (например, RGA для текста).** Отклонено на этом этапе: сложность
  несоразмерна выигрышу для коротких полей задачи. Возможный кандидат,
  если появится совместное редактирование описаний.

## Последствия

- Сервер обязан хранить `field_versions` (JSONB) рядом с задачей.
- Клиент обязан отправлять только изменённые поля, а не весь объект.
- Нужны тесты на одновременное редактирование с двух устройств —
  включены в план проверок §13 ТЗ.
- Пользователю требуется понятный индикатор «изменено на другом устройстве».

## Уточнение этапа 5 (2026-11-13)

Реализация уточнила три места, которые на этапе 1 были описаны схематично.

**Метки времени клиента ограничиваются временем сервера.** Часы устройства
могут уходить вперёд; без ограничения телефон с часами на сутки вперёд
выигрывал бы все конфликты сутки подряд. Метка из будущего заменяется
текущим временем сервера, метка поля хранится как максимум из принятых.

**Быстрый путь.** Если `baseVersion == version`, клиент видел актуальное
состояние, и его правка применяется без сравнения меток — даже если часы
устройства отстают. Сравнение включается только при параллельных правках.

**Исполнители — не чистый OR-Set.** В классическом OR-Set одновременные
add и remove одного элемента разрешаются в пользу add. Здесь для одного
человека побеждает операция, **пришедшая на сервер позже**: у каждой
строки `task_assignees` есть `assigned_at` и `removed_at`, и сервер
гарантирует, что новая метка строго больше предыдущей
(`GREATEST(now, previous + 1 µs)`). Причины:

- метки ставит сервер, а не клиент, поэтому «одновременности» в смысле
  OR-Set на сервере не бывает — операции упорядочены транзакцией;
- пользователь, снявший исполнителя, ожидает, что тот снят, даже если
  назначение было в ту же миллисекунду; правило «add побеждает» в этом
  случае выглядело как ошибка (поймано интеграционным тестом).

Свойство, ради которого выбирался OR-Set, сохранено: назначения **разных**
людей с двух устройств не затирают друг друга, потому что клиент шлёт
дельты `add`/`remove`, а не итоговый набор.

**Проигравшая правка в истории.** Каждое отклонённое поле записывается
в `task_events` с типом `EDIT_REJECTED` и отклонённым значением,
а в ответе перечисляется в `conflicts`. Клиент показывает уведомление
«изменено на другом устройстве» и принимает серверную версию.
