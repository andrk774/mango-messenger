# ADR-0005: Разрешение конфликтов — per-field LWW для задач, OR-Set для исполнителей

- **Статус:** принято
- **Дата:** 2026-11-12
- **Этап:** 1

## Контекст

Сообщения по своей природе append-only: их почти не редактируют, и конфликтов
практически не возникает. Задачи — изменяемые объекты, которые правят с
нескольких устройств и несколько человек одновременно. Нужна политика,
понятная пользователю и не теряющая данные молча.

Простая блокировка по версии всего объекта (отклонять PATCH при расхождении)
на практике означает: один человек поменял срок, другой в это же время —
приоритет, и второй получает ошибку, хотя конфликта по сути нет.

## Решение

| Поле | Стратегия | Обоснование |
|---|---|---|
| `title`, `description` | LWW по полю | Текст редко правят одновременно |
| `status` | LWW по полю; при равных метках времени выигрывает больший `conflictWeight` (DONE > CANCELLED > REVIEW > IN_PROGRESS > TODO) | Завершение — более сильное намерение, чем возврат в работу |
| `priority`, `due_at` | LWW по полю | — |
| `assignees` | **OR-Set**: add и remove применяются независимо | Два человека назначили разных исполнителей — остаются оба; потеря назначения заметнее, чем лишнее |
| `comments`, `attachments` | append-only, дедуп по `client_op_id` | Конфликтов нет по построению |
| `subtasks` | append-only + LWW по каждой подзадаче | — |

Механика: клиент отправляет `PATCH /tasks/{id}` с `baseVersion` и **только
изменёнными полями** плюс метки времени изменения по каждому полю. Сервер:

1. `baseVersion == version` → применяет, `version++`;
2. `baseVersion < version` → применяет per-field LWW, возвращает `200`
   с итоговым объектом и списком `conflicts`;
3. клиент принимает серверный объект как истину и, если его правка
   проиграла, показывает ненавязчивое уведомление.

Каждое изменение пишется в `task_events`. Это ключевая страховка: даже
проигравшая правка остаётся в истории, и конфликт можно разобрать постфактум.

## Альтернативы

- **Блокировка по версии всего объекта.** Отклонено: ложные конфликты при
  правках разных полей.
- **Последняя запись побеждает целиком (object-level LWW).** Отклонено:
  молча теряет параллельные изменения других полей.
- **CRDT (например, RGA для текста).** Отклонено на этом этапе: сложность
  несоразмерна выигрышу для коротких полей задачи. Возможный кандидат,
  если появится совместное редактирование описаний.

## Последствия

- Сервер обязан хранить `field_versions` (JSONB) рядом с задачей.
- Клиент обязан отправлять только изменённые поля, а не весь объект.
- Нужны тесты на одновременное редактирование с двух устройств —
  включены в план проверок §13 ТЗ.
- Пользователю требуется понятный индикатор «изменено на другом устройстве».
