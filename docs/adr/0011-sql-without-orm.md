# ADR-0011: Доступ к PostgreSQL — прямой SQL поверх JDBC, без ORM

- **Статус:** принято
- **Дата:** 2026-11-12
- **Этап:** 3

## Контекст

Схема Mango опирается на возможности PostgreSQL, от которых зависит
корректность, а не удобство:

- **частичные уникальные индексы** — `UNIQUE (email) WHERE deleted_at IS NULL`;
- **`INSERT ... ON CONFLICT DO NOTHING RETURNING`** — отличает «уже есть»
  от ошибки, не прерывая транзакцию;
- **`UPDATE ... RETURNING`** — атомарная выдача порядкового номера сообщения
  и одноразовое гашение токена из письма;
- **JSONB** — `field_versions` для разрешения конфликтов по полям;
- **citext** — регистронезависимые email и username;
- **GIN по `to_tsvector`** — полнотекстовый поиск.

ORM эти конструкции либо не выражает, либо выражает через «escape hatch»,
то есть через тот же сырой SQL, но спрятанный и хуже проверяемый.

Отдельное наблюдение из этого же этапа: в PostgreSQL **любая ошибка
ограничения прерывает транзакцию**. Код, который ловит нарушение
уникальности и продолжает работу в той же транзакции, обречён упасть
на `commit`. Такие места надо видеть, а не угадывать за абстракцией.

## Решение

Доступ к данным — прямой SQL через JDBC с тонким слоем помощников
(`Connection.query`, `queryOne`, `update`, типизированное чтение колонок).
Пул соединений — HikariCP. Транзакциями управляет сервис, репозиторий
принимает `Connection` параметром.

Вместо ORM-маппинга — явные функции отображения `ResultSet → запись`.

## Альтернативы

- **Exposed (JetBrains).** Отклонено: JSONB, citext и `ON CONFLICT`
  с предикатом требуют пользовательских типов и сырых фрагментов, что
  сводит выигрыш к нулю, оставляя стоимость абстракции.
- **Hibernate/JPA.** Отклонено: кеш первого уровня и ленивая загрузка
  делают поведение запросов непредсказуемым; в приложении с жёсткими
  требованиями к порядку событий это опасно.
- **jOOQ.** Серьёзный кандидат: типобезопасный SQL без сокрытия семантики.
  Отклонено на этом этапе из-за шага генерации кода из схемы, который
  усложняет сборку. К пересмотру, когда число запросов вырастет.

## Последствия

- SQL виден целиком и проверяется интеграционными тестами на настоящем
  PostgreSQL, а не на встроенной базе-заменителе.
- Больше ручного кода отображения. Это принятая цена.
- Ошибки в именах колонок обнаруживаются тестом, а не компилятором.
  Отсюда требование: **каждый запрос обязан быть покрыт тестом**.
- Чтение `ResultSet.getLong` для NULL возвращает 0 — поэтому в помощниках
  есть отдельные `longOrNull`/`intOrNull`, и использовать голые геттеры
  для необязательных колонок запрещено.
