# ADR-0013: Ротация refresh token и реакция на повторное использование

- **Статус:** принято
- **Дата:** 2026-11-12
- **Этап:** 3

## Контекст

Refresh token живёт неделями и даёт полный доступ к учётной записи.
На мобильном устройстве он хранится в зашифрованном виде
([ADR-0008](0008-token-storage.md)), но утечка всё равно возможна:
резервная копия, вредоносное приложение, отладочный доступ.

Долгоживущий неизменяемый токен означает, что однажды украденное
значение работает до истечения срока, и обнаружить кражу невозможно.

## Решение

### Ротация

Каждый обмен refresh token порождает **новый** refresh token, а старый
немедленно отзывается с причиной `ROTATED`. Записи сессий не удаляются,
а помечаются: по полю `previous_session_id` восстанавливается цепочка
обменов.

В базе хранится **только SHA-256 от токена**. Медленный хеш здесь не нужен:
токен — 256 бит из криптографически стойкого источника, перебору
не поддаётся, а обновление токена не должно стоить 64 МиБ памяти.

### Обнаружение повторного использования

Если пришёл refresh, сессия которого уже отозвана, это значит, что
значение есть у двух сторон: законного владельца и того, кто его получил.
Различить их невозможно — оба предъявляют одинаково действительный токен.

Поэтому отзываются **все** сессии пользователя. Законный владелец входит
заново, злоумышленник теряет доступ. Неудобство для одного против
сохранности учётной записи — выбор очевиден.

### Отзыв при смене пароля

Смена пароля отзывает все сессии: восстановление доступа после кражи
не должно оставлять злоумышленнику действующий вход.

## Альтернативы

- **Неизменяемый refresh до истечения срока.** Отклонено: кражу
  невозможно обнаружить, украденный токен работает недели.
- **Отзывать только скомпрометированную сессию.** Отклонено: неизвестно,
  какая из двух сессий принадлежит злоумышленнику — он мог обменять
  токен первым, и тогда «законной» окажется его сессия.
- **Хранить refresh в открытом виде.** Отклонено: дамп базы сразу даёт
  доступ ко всем учётным записям.

## Последствия

- Клиент обязан сохранять новый refresh после каждого обновления.
  Потеря ответа на запрос обновления означает выход из системы — это
  приемлемо и прямо следует из механизма.
- Параллельные обновления с одного устройства (две корутины сразу)
  выглядят как повторное использование. Клиент обязан сериализовать
  обновление токена; на Android это уже обеспечено очередью операций.
- **Отзыв сессий обязан фиксироваться в базе до выбрасывания ошибки.**
  Исключение, брошенное внутри транзакции, откатывает её целиком —
  вместе с отзывом. Ошибка этого рода была допущена при реализации и
  найдена тестом `повторное использование refresh token завершает все сессии`;
  теперь результат операции возвращается значением, а отказ формируется
  после фиксации транзакции.
- Таблица `sessions` растёт: каждая ротация добавляет строку. Требуется
  фоновая очистка отозванных сессий старше срока хранения.
