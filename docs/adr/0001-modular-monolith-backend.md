# ADR-0001: Backend — модульный монолит на Ktor, не микросервисы

- **Статус:** принято
- **Дата:** 2026-11-12
- **Этап:** 1

## Контекст

Мессенджер с задачами состоит из нескольких предметных областей: авторизация,
переписка, задачи, real-time, уведомления, вложения. Соблазн сразу разнести их
по сервисам велик, потому что «так масштабируется».

Фактическая ситуация: продукт на нулевой стадии, нагрузки нет, команда — один
исполнитель, а требования ещё будут меняться. Микросервисы в этих условиях
добавляют распределённые транзакции, версионирование межсервисных контрактов,
отдельный деплой и трассировку — всё это стоит времени, которое сейчас нужно
на функциональность.

## Решение

Backend реализуется как **модульный монолит** на Ktor: один развёртываемый
процесс, внутри — модули `auth`, `messaging`, `tasks`, `realtime`, `sync`,
`notifications`, `storage`, `common`.

Модули общаются **только через публичные интерфейсы сервисов**. Прямое
обращение к таблицам чужого модуля запрещено. Это и есть будущая граница
сервиса: выделение модуля в отдельный процесс сводится к замене вызова
интерфейса на сетевой вызов.

## Альтернативы

- **Микросервисы сразу.** Отклонено: цена инфраструктуры несоразмерна текущей
  стадии, а границы предметных областей ещё не устоялись — разрезать по живому
  придётся всё равно, но уже через сетевые контракты.
- **Монолит без внутренних границ.** Отклонено: без дисциплины модулей
  разделение позже становится невозможным практически.

## Последствия

- Простой локальный запуск: один `docker compose up`.
- Транзакции внутри одной БД — не нужны саги для операций вроде
  «создать задачу из сообщения».
- Обязательная дисциплина: любое обращение в чужой модуль через интерфейс,
  даже когда «быстрее сделать JOIN». Это проверяется на ревью.
- Горизонтальное масштабирование — репликами всего процесса. Для реального
  трафика real-time потребуется вынести WebSocket-слой; схема к этому готова
  за счёт fan-out через Redis pub/sub.
