# ADR-0018: Видимость задач и права на изменение

- **Статус:** принято
- **Дата:** 2026-11-13
- **Этап:** 5

## Контекст

Задача может быть личной, может жить в чате, может быть создана из
сообщения. ТЗ не задаёт явно, кто её видит и кто вправе менять.
Без единого правила появляются дыры двух видов: задача из закрытого чата
видна постороннему через список «Назначенные мне», либо человек,
которого назначили, не может отметить задачу выполненной.

Правило нужно одно — и для REST, и для рассылки событий журнала:
если список получателей события считается иначе, чем права на чтение,
клиент получает событие о задаче, которую потом не может открыть,
или наоборот не узнаёт об изменении видимой задачи.

## Решение

**Видит задачу** (и получает её события) тот, кто выполняет хотя бы одно:

1. создал её;
2. назначен исполнителем сейчас (`removed_at IS NULL OR assigned_at > removed_at`);
3. состоит в чате, к которому привязана задача.

Это правило записано в SQL один раз (`TasksRepository.VISIBLE_TO`) и
используется и для проверки доступа, и для списка получателей события
(`recipients` — объединение тех же трёх множеств). Несуществующая,
удалённая и чужая задача дают **один и тот же** ответ `403 «Задача недоступна»`:
по ответу нельзя узнать, существует ли задача с таким идентификатором.

Исключение — повторное удаление автором: оно отвечает `204` без нового
события, чтобы повтор из очереди клиента после потерянного ответа
не выглядел окончательным отказом.

**Права:**

| Действие | Кто |
|---|---|
| Читать, править поля, менять исполнителей, комментировать | любой, кто видит задачу |
| Удалить | только создатель |
| Создать задачу в чате / из сообщения | только участник этого чата |

**Ограничения на исполнителей:**

- задача чата — исполнителями могут быть только участники чата;
- личная задача (без чата) — только сам создатель.

Второе ограничение не косметика: иначе личная задача становилась бы
способом показать произвольный текст любому пользователю системы
по его идентификатору — канал спама в обход чатов и блокировок.

**Рассылка при смене состава.** Событие об изменении исполнителей уходит
объединению получателей **до и после** изменения: снятый исполнитель
должен узнать, что задача у него пропала, иначе она останется в его
локальном списке навсегда. По той же причине событие удаления
рассылается списку, посчитанному до удаления.

## Альтернативы

- **Права по ролям (владелец / редактор / наблюдатель).** Отклонено для MVP:
  в мессенджере-трекере для небольших команд роль почти всегда совпадает
  с «участник чата», а отдельная модель прав — это экраны настройки,
  которых пользователь не просил. Вернуться, если появятся рабочие
  пространства с внешними участниками.
- **Удаление любым участником.** Отклонено: удаление необратимо для
  остальных, а правка поля — нет (её видно в истории).
- **`404` для отсутствующей и `403` для чужой задачи.** Отклонено:
  различие кодов позволяет перебором узнавать существование задач.

## Последствия

- Выход из чата автоматически лишает доступа к его задачам, кроме
  созданных или назначенных лично — отдельной чистки не нужно.
- Клиент при получении `403` на задачу, которая есть локально,
  должен считать её недоступной (пока это делается через полную
  перезагрузку списка задач; точечная обработка — долг этапа 6).
- Изменение правила требует правки ровно одного SQL-фрагмента;
  интеграционные тесты проверяют и доступ, и получателей событий.
