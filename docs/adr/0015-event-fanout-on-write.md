# ADR-0015: Журнал событий — строка на получателя (fan-out на запись)

- **Статус:** принято
- **Дата:** 2026-11-12
- **Этап:** 4

## Контекст

Клиенту нужен способ узнать всё, что он пропустил, по одному курсору.
Это требование из [ADR-0006](0006-websocket-is-not-the-only-channel.md):
WebSocket лишь ускоряет доставку, а источник истины — журнал.

Устройство журнала можно выбрать двумя способами:

1. **Fan-out на запись.** Одно изменение превращается в N строк, по одной
   на получателя. У клиента ровно один курсор; «что я пропустил» —
   это `WHERE user_id = ? AND id > ?`.
2. **Общий журнал на чат.** Одна строка на изменение, клиент хранит курсор
   на каждый чат. Запись дешевле, но догонка превращается в обход всех
   чатов с объединением результатов.

## Решение

Выбран **fan-out на запись**. Таблица `sync_events` содержит строку
на каждого получателя; вставка выполняется одним многострочным запросом
в той же транзакции, что и само изменение.

Запись события и изменение данных **обязаны фиксироваться вместе**.
Иначе возможны два испорченных состояния: сообщение есть, а события нет
(клиент никогда о нём не узнает), либо событие есть, а сообщения нет
(клиент получит ссылку в пустоту).

## Альтернативы

- **Общий журнал на чат.** Отклонено: переносит сложность на клиента,
  где её труднее всего отлаживать, и требует хранить и согласовывать
  десятки курсоров вместо одного.
- **Чтение журнала из таблиц данных по времени изменения.** Отклонено:
  время на разных узлах расходится, а удаления в таком журнале не видны
  вовсе.

## Последствия

- **Усиление записи.** Сообщение в группе из 50 человек порождает
  50 строк. Для личных переписок и небольших групп это незначительно;
  для крупных групп решение придётся пересмотреть. Это зафиксированное
  ограничение, а не незамеченный недостаток.
- Журнал растёт и требует усечения. Усечение делает курсоры старых
  клиентов недействительными, поэтому сервер отвечает `410 Gone`
  со списком областей для перезагрузки, а клиент перезагружает
  **только их**, а не всю базу.
- Рассылка в реальном времени отделена от записи: события публикуются
  **после** фиксации транзакции. Неудавшаяся публикация не теряет
  событие — клиент получит его при следующей сверке.
