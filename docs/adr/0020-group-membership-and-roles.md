# ADR-0020: Состав группы и роли

- **Статус:** принято
- **Дата:** 2026-11-13
- **Этап:** 6a

## Контекст

Схема с этапа 1 предусматривала роли `OWNER`, `ADMIN`, `MEMBER`, но правил
не было: кто кого может исключить, что происходит при уходе владельца,
как об изменениях узнают участники. Без правил возможны тупики (группа
без владельца, которой никто не может управлять) и конфликты (два
администратора исключают друг друга).

## Решение

**Права:**

| Действие | OWNER | ADMIN | MEMBER |
|---|---|---|---|
| Переименовать, добавить участников | да | да | нет |
| Исключить участника (`MEMBER`) | да | да | нет |
| Исключить администратора | да | нет | нет |
| Назначить/снять администратора, передать владение | да | нет | нет |
| Выйти из группы | да | да | да |

**Ровно один владелец.** Назначение другого владельцем — передача:
прежний становится администратором. Если владелец уходит, владение
автоматически переходит самому давнему администратору, при их
отсутствии — самому давнему участнику. Ушёл последний — группа удаляется.

**Сериализация.** Каждое изменение состава берёт ту же блокировку строки
чата (`FOR UPDATE`), что и выдача номеров сообщений. Иначе два
одновременных добавления могли бы вместе превысить предел (201 участник)
или породить два системных сообщения о добавлении одного человека.

**Идемпотентность.** Добавление уже состоящего и удаление уже выбывшего —
успех без последствий: повтор запроса после обрыва связи не ломает историю.

**Системные сообщения.** Каждое изменение пишется в переписку как сообщение
`SYSTEM` со структурой события в общей нумерации — изменения видны на
своём месте в истории, клиент, пропустивший события, узнаёт о них при
обычной догрузке. Текст собирает клиент: сервер не знает ни языка,
ни грамматического рода участника. Системные сообщения не считаются
непрочитанными.

**События журнала:**

- новым участникам — `CONVERSATION_CREATED` (их собственная карточка чата);
- остальным — `CONVERSATION_MEMBER_ADDED` / `_UPDATED` и обновлённая карточка;
- выбывшему **и** оставшимся — `CONVERSATION_MEMBER_REMOVED`: устройство
  выбывшего удаляет чат вместе с перепиской.

**Карточка чата строится для каждого получателя.** До этапа 6a событие
`CONVERSATION_CREATED` уходило всем с карточкой, собранной для автора:
собеседник видел в заголовке личного чата своё же имя, а участники
группы — роль `OWNER`. Теперь `conversationViews` строит карточку
отдельно для каждого получателя.

**Доступ после выхода.** Выбывший теряет доступ к истории, файлам группы
и задачам чата (кроме созданных им или назначенных ему — ADR-0018).
История новым участникам видна целиком.

**Управление составом на клиенте — только при наличии сети.** Операции
не ставятся в очередь: решение о правах принимает сервер, и оптимистичное
«участник исключён» с последующим откатом вводило бы в заблуждение.

## Альтернативы

- **Несколько владельцев.** Отклонено: споры двух равных владельцев не
  разрешаются правилами.
- **Группа без владельца после его ухода.** Отклонено: никто не смог бы
  назначать администраторов.
- **Скрытие истории до вступления.** Отложено: требует фильтра по
  `joined_at` во всех запросах истории, поиска и вложений. Для рабочих
  групп полная история обычно полезнее.

## Последствия

- Изменение состава большой группы — одна транзакция с fan-out на каждого
  участника (до 201 строки журнала на событие) плюс карточка на каждого.
  Для групп в тысячи человек понадобится иная модель (ADR-0015).
- Правила дублируются на клиенте только для показа кнопок; решает сервер.
