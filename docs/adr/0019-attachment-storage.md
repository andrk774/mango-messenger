# ADR-0019: Хранение вложений — файловое хранилище за интерфейсом, подписанные ссылки

- **Статус:** принято
- **Дата:** 2026-11-13
- **Этап:** 6a

## Контекст

План (ADR-0001, OpenAPI этапа 1) предполагал MinIO: клиент получает
presigned-ссылку и грузит файл прямо в объектное хранилище, минуя сервер.
На этапе 3 выяснилось, что образы MinIO недоступны для анонимной загрузки
(Docker Hub — 404, quay.io — 401). Другие S3-совместимые хранилища
(SeaweedFS, Garage) добавили бы в локальный стек сервис с собственной
настройкой ключей и бакетов ради одной функции.

При этом от хранилища требуется немного: записать поток, отдать поток,
удалить.

## Решение

1. **Интерфейс `BlobStorage`** (`write` с пределом размера, `open`,
   `delete`). Сейчас единственная реализация — `FileSystemBlobStorage`:
   каталог на диске, в Docker — именованный том `attachments`.
2. **Подписанные ссылки выдаёт сервер** (`UrlSigner`, HMAC-SHA256 от
   действия, вложения и срока). Загрузка — `PUT`, скачивание — `GET`
   по этим ссылкам, без токена пользователя. Ссылки на загрузку живут
   15 минут, на скачивание — 5.
3. **Клиент не знает, куда ведёт ссылка.** Ответ содержит `uploadUrl`/`url`,
   которые могут быть относительными (сейчас) или абсолютными (S3).
   Передача файлов на Android идёт клиентом OkHttp **без** подстановки
   токена — при переходе на внешнее хранилище токен не уйдёт постороннему.
4. **Проверка файла при приёме:**
   - белый список типов; SVG и HTML запрещены (исполняют скрипты);
   - пределы: картинки 20 МБ, прочее 100 МБ; принимается не больше
     заявленного размера — проверка на каждом блоке, а не после записи;
   - сверка SHA-256 с заявленным клиентом;
   - сигнатура содержимого (первые байты) должна соответствовать типу.
   Расхождение размера или хеша — ошибка передачи (400, повтор возможен);
   расхождение сигнатуры — подлог (415, файл отклонён окончательно).
5. **Отдача:** картинки — `Content-Disposition: inline`, остальное —
   `attachment`; всегда `Content-Security-Policy: default-src 'none'; sandbox`
   и `X-Content-Type-Options: nosniff`. Имя файла очищается от путей,
   кавычек и управляющих символов и передаётся в двух видах (ASCII и
   `filename*` UTF-8).
6. **Права:** автор видит свой файл всегда (превью до отправки), остальные —
   только если файл в неудалённом сообщении чата, где они состоят сейчас.
   Проверка — при выдаче ссылки, а не при скачивании.
7. **Привязка к сообщению** — одним `UPDATE ... WHERE owner = отправитель
   AND conversation = этот чат AND scan_status = 'CLEAN' AND message_id IS NULL`
   в транзакции отправки. Не привязалось хоть одно — откат всего сообщения.

## Альтернативы

- **SeaweedFS/Garage в стеке.** Отложено: лишний сервис в разработке.
  Реализация `S3BlobStorage` + выдача настоящих presigned-ссылок — работа
  одного модуля, клиенты не меняются.
- **Загрузка multipart через API с токеном.** Отклонено: тогда переход на
  прямую загрузку в хранилище изменил бы протокол клиента.
- **Отдача файла без подписанной ссылки, по токену.** Отклонено: `AsyncImage`
  и внешние приложения (просмотр PDF) не умеют подставлять заголовок
  авторизации, а токен в адресе попадал бы в журналы.

## Последствия

- Сервер сам принимает и отдаёт байты: на одном экземпляре это нормально,
  при нескольких каталог должен быть общим томом — или пора на S3.
- **Это не антивирус.** Сигнатура ловит переименованный исполняемый файл
  или HTML под видом картинки, но не вредоносный PDF или макрос в docx.
  Статус `CLEAN` означает «прошёл проверку типа», не более.
- Нет очистки: вложения без сообщения (разрешение выдано, сообщение не
  отправлено) и файлы удалённых сообщений остаются на диске. Ограничитель —
  не более 50 непривязанных разрешений в сутки на пользователя. Фоновая
  очистка — технический долг.
- Нет докачки (Range) — для больших видео это заметно.
