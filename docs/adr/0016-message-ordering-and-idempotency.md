# ADR-0016: Порядок сообщений через блокировку чата, идемпотентность — через уникальный индекс

- **Статус:** принято
- **Дата:** 2026-11-12
- **Этап:** 4

## Контекст

Два требования пересекаются в одной операции отправки сообщения:

1. **Порядок.** Внутри чата сообщения обязаны иметь строго возрастающие
   номера без пропусков: по ним клиент определяет, не пропустил ли он
   что-то, и по ним же строит пагинацию.
2. **Идемпотентность.** Клиент повторяет отправку при неизвестном исходе,
   и повтор не должен создавать второе сообщение.

Наивная реализация нарушает оба: два одновременных запроса читают
`last_event_seq`, получают одинаковое значение и сталкиваются на
уникальном индексе — вместо упорядочивания получается отказ.

## Решение

### Порядок

Счётчик живёт в строке чата (`conversations.last_event_seq`). Отправка
начинается с `SELECT ... FOR UPDATE` по этой строке, что сериализует
одновременные отправки в один чат. Номер выдаётся
`UPDATE ... RETURNING last_event_seq`.

Номер **не освобождается** при удалении сообщения: строка остаётся
с пометкой `deleted_at`. Пропуск в нумерации клиент истолковал бы как
пропущенное сообщение и запустил бы ненужную догонку.

### Идемпотентность

Ключ — `clientMsgId`, присвоенный устройством до отправки. Защита —
уникальный индекс `(conversation_id, sender_id, client_msg_id)`.

Отдельная запись в журнале идемпотентности (`outbox_operations`)
для сообщений **не делается**: индекс уже обеспечивает инвариант,
а дублирование той же гарантии во втором месте создало бы два
источника истины для одного правила.

**Порядок операций важен:** блокировка берётся ДО проверки на повтор.
Иначе два одновременных повтора одной операции прошли бы проверку оба
и столкнулись на индексе, прервав транзакцию, — вместо того чтобы
вернуть одно и то же сообщение.

Ответ различает исходы кодом состояния: `201` — сообщение создано,
`200` — операция уже выполнялась ранее.

## Альтернативы

- **Номер из последовательности PostgreSQL.** Отклонено: последовательности
  не откатываются, и отменённая транзакция оставляла бы дыру в нумерации.
- **Номер по времени создания.** Отклонено: часы узлов расходятся,
  а при равных метках порядок неопределён.
- **Оптимистичная вставка с повтором при конфликте.** Отклонено: ошибка
  ограничения прерывает транзакцию в PostgreSQL, то есть повтор означает
  новую транзакцию и ещё одно обращение к базе.
- **Журнал идемпотентности для сообщений.** Отклонено как дублирование
  гарантии, которую уже даёт схема. Журнал остаётся для операций без
  естественного ключа дедупликации — например, изменений задач.

## Последствия

- Отправки в один чат сериализуются. Это узкое место для очень активных
  групп; для личных переписок и обычных групп блокировка держится
  доли миллисекунды.
- Блокировка берётся на строку чата, а не на таблицу: отправки в разные
  чаты идут параллельно.
- Проверено тестами: двенадцать одновременных отправок дают номера
  от 1 до 12 без пропусков и повторов; повторная отправка возвращает
  то же сообщение с кодом 200.
