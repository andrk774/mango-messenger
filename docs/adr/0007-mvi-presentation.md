# ADR-0007: MVI в presentation-слое поверх MVVM

- **Статус:** принято
- **Дата:** 2026-11-12
- **Этап:** 2

## Контекст

В ТЗ указаны и MVVM, и MVI. Это не противоречие: MVVM задаёт, где живёт
состояние (ViewModel), MVI — как оно меняется (единый неизменяемый объект
состояния и явные намерения).

В Compose особенно вреден разброс состояния по нескольким
`MutableStateFlow`: поля расходятся между собой, а каждое независимое
изменение вызывает отдельную рекомпозицию.

## Решение

- Каждый экран имеет **один** `data class XxxUiState` и выдаёт его как
  `StateFlow<XxxUiState>`.
- Состояние собирается через `combine` источников и публикуется
  `stateIn(scope, SharingStarted.WhileSubscribed(5_000), initial)`.
  Пятисекундное окно переживает поворот экрана без перезапроса данных.
- Действия пользователя — методы ViewModel (`onStatusChange`, `onSearchQueryChange`).
- Разовые события (snackbar, навигация) идут через отдельный
  `SharedFlow`, а не через поле состояния: иначе они повторно
  «проигрываются» после поворота экрана.
- Compose читает состояние через `collectAsStateWithLifecycle()`: в фоне
  подписка останавливается.

## Альтернативы

- **Отдельные StateFlow на каждое поле.** Отклонено: рассинхрон полей
  и лишние рекомпозиции.
- **Полноценная библиотека MVI с редьюсерами и middleware.** Отклонено:
  на текущем объёме логики добавляет церемонию без выигрыша.

## Последствия

- Для списков обязателен стабильный `key` в `items(...)`, иначе выигрыш
  от неизменяемого состояния съедается пересозданием элементов.
- Любое поле, влияющее на отрисовку, обязано попасть в `UiState` —
  скрытого состояния в композаблах быть не должно (исключение —
  чисто локальные вещи вроде видимости пароля).
