# План безопасности Mango Messenger

Документ описывает модель угроз и меры защиты. Разделяет **реализованное**,
**запланированное** и **сознательно не заявленное**.

---

## 1. Что защищаем

| Актив | Почему важен |
|---|---|
| Содержимое переписки | Основной предмет приватности пользователя |
| Refresh token | Долговременный доступ к аккаунту |
| Задачи и комментарии | Часто содержат внутреннюю информацию организации |
| Вложения | Документы, фотографии, голосовые сообщения |
| Метаданные (кто с кем, когда) | Раскрывают связи даже без содержимого |
| Email и список контактов | Персональные данные |

## 3. Реализовано и проверено

### 3.1. Хранение токенов

Подробно: [ADR-0008](../adr/0008-token-storage.md).

- AES-256 ключ генерируется **внутри** Android Keystore и не покидает его.
- AES/GCM/NoPadding — AEAD: конфиденциальность + обнаружение подмены.
- IV случаен для каждой операции, `setRandomizedEncryptionRequired(true)`.
- `commit()` вместо `apply()`: потеря токенов при падении недопустима.
- Неудачная расшифровка → сессия стирается и требуется повторный вход,
  вместо падения приложения.

Проверено 7 тестами, включая `tokens are encrypted before being written`:
тест явно убеждается, что ни access, ни refresh token не видны в хранилище
открытым текстом.

**Непроверенное:** сам `KeystoreCrypto` требует инструментального теста на
устройстве. В тестах он подменён управляемой реализацией, поэтому
взаимодействие с реальным Keystore **не проверено**.

### 3.2. Персональные данные в логах

Объект `Redact` (`:core:common`) обрабатывает:

| Данные | Результат |
|---|---|
| Email | `a***@example.com` — домен сохраняется для диагностики |
| Токен | `<redacted>` — никогда частично |
| Текст сообщения | `<text:42>` — только длина |
| Идентификатор | первые 8 символов — достаточно для корреляции логов |
| Произвольный текст | вычищаются Bearer-токены, JWT, email, телефоны |

Фильтрация выполняется **в точке записи**, а не полагается на дисциплину
«не логировать лишнего»: логи уезжают в crash-репортинг, попадают в
bugreport и остаются на диске.

Проверено 10 тестами.

### 3.3. Резервное копирование

`allowBackup=false` и явные правила `data_extraction_rules.xml`,
исключающие все домены. База содержит переписку, а зашифрованные токены на
другом устройстве всё равно нерабочие — копия была бы одновременно
бесполезной и опасной.

### 3.4. Приватность по умолчанию

Закреплено тестом `defaults are safe for privacy`:

- показ текста сообщения в уведомлении — **выключен**;
- загрузка медиа — только по Wi-Fi;
- отчёты о прочтении и индикатор набора — включены (ожидаемое поведение
  мессенджера, отключается пользователем).

### 3.5. Защита от дубликатов операций

Три независимых рубежа: уникальный индекс в Room, уникальный индекс в
PostgreSQL, `Idempotency-Key` в HTTP. Клиентская часть проверена 13 тестами.

## 4. Запланировано (Этапы 3–7)

### 4.1. Авторизация — РЕАЛИЗОВАНО на Этапе 3

Ниже описано фактическое поведение; отличия от первоначального плана
отмечены отдельно.

- Пароли: **Argon2id** (не bcrypt, не PBKDF2). Параметры стоимости
  хранятся **внутри строки хеша**, а не в конфигурации — иначе их
  повышение разом обесценило бы все существующие пароли
  ([ADR-0012](../adr/0012-argon2id-bouncycastle.md)).
- Access token — JWT, короткий срок жизни (15 мин).
- Refresh token — непредсказуемая строка, в БД хранится **только хеш**.
- **Ротация refresh token** при каждом обновлении. Повторное использование
  старого refresh token трактуется как компрометация: все сессии
  пользователя отзываются ([ADR-0013](../adr/0013-refresh-rotation-and-reuse-detection.md)).
  Отзыв фиксируется в базе **до** выбрасывания ошибки: исключение
  из тела транзакции откатило бы его вместе с собой.
- Токен WebSocket передаётся в **первом кадре AUTH**, а не в URL: URL
  попадает в логи прокси и в историю.

### 4.2. Защита от IDOR — РЕАЛИЗОВАНО на Этапе 4

Принципиальное требование: доступ проверяется **не по непредсказуемости
идентификатора**, а явным условием.

Каждая операция с сообщениями начинается с проверки участия в чате.
Ответ для чужого и для несуществующего чата **одинаков** — иначе перебором
можно было бы выяснять, какие чаты существуют. Закреплено тестом
`несуществующий чат и чужой чат отвечают одинаково`.

```sql
-- Правильно: доступ доказывается членством
SELECT m.* FROM messages m
WHERE m.id = :messageId
  AND EXISTS (
      SELECT 1 FROM conversation_members cm
      WHERE cm.conversation_id = m.conversation_id
        AND cm.user_id = :currentUserId
        AND cm.left_at IS NULL
  );
```

Правило: ни один запрос к `messages`, `tasks`, `attachments` не выполняется
без условия принадлежности. Это проверяется отдельными тестами, включая
сценарий «пользователь удалён из чата → 403».

### 4.3. Ограничение частоты — РЕАЛИЗОВАНО на Этапе 3

Фактические значения:

| Эндпоинт | Предел | Ключ |
|---|---|---|
| `POST /v1/auth/login` | 5 за 15 минут | адрес почты + адрес клиента |
| `POST /v1/auth/register` | 3 за час | адрес клиента |
| `POST /v1/auth/password/forgot` | 3 за час | адрес почты |

**Ограничение:** счётчики лежат в памяти процесса, поэтому при нескольких
экземплярах фактический предел умножается на их число. Перенос в Redis —
Этап 4.

Ответ на превышение содержит заголовок `Retry-After`.

Первоначально планировалось (остаётся в силе для будущих эндпоинтов):

| Эндпоинт | Лимит |
|---|---|
| `POST /auth/login` | 5 попыток за 15 мин на пару (email, IP), затем экспоненциальная задержка |
| `POST /auth/register` | 3 в час на IP |
| `POST /auth/password/forgot` | 3 в час на email |
| Отправка сообщений | 30 в минуту на пользователя |
| Загрузка вложений | 20 в час на пользователя |

Хранилище счётчиков для многоэкземплярной установки — Redis (Этап 4).

Ответ на неверный пароль и на несуществующий email должен быть
**неотличим** по тексту и по времени — иначе эндпоинт превращается в
перечислитель зарегистрированных адресов.

### 4.4. Вложения

- Загрузка по presigned URL напрямую в S3/MinIO, минуя backend.
- Ограничение размера на уровне presigned-политики, а не только на клиенте.
- Проверка заявленного MIME против фактической сигнатуры файла.
- `checksum_sha256` для дедупликации и контроля целостности.
- `scan_status`: `PENDING → CLEAN | REJECTED`; до `CLEAN` файл не отдаётся.
- Скачивание — presigned GET с коротким TTL **после** проверки прав.
- `Content-Disposition: attachment` и `X-Content-Type-Options: nosniff`.

### 4.5. Deep links

- Явный список поддерживаемых путей; всё остальное отбрасывается.
- Параметры валидируются как недоверенный ввод.
- Переход к чату или задаче **не обходит** проверку прав: экран всё равно
  запрашивает данные, и сервер отвечает 403, если доступа нет.
- App Links с верификацией домена (`assetlinks.json`).

### 4.6. Сеть

- `cleartextTrafficPermitted=false`.
- Certificate pinning рассматривается после стабилизации домена; пиннинг с
  единственным ключом без резервного — способ заблокировать себе доставку
  обновлений.

### 4.7. Проверка зависимостей

- OWASP Dependency-Check или `gradle versions` + аудит в CI.
- Сборка помечается неуспешной при наличии известной уязвимости высокой
  степени.

## 5. Сознательно НЕ заявлено

### Сквозное шифрование

**Mango Messenger не использует сквозное шифрование.** Сообщения защищены
TLS в канале и хранятся на сервере в открытом виде.

Это зафиксировано в [ADR-0009](../adr/0009-no-e2ee-claims.md). Заявление об
E2EE допустимо только после реализации проверенного протокола, управления
ключами, поддержки нескольких устройств, верификации собеседника и
соответствующих тестов.

Точки расширения заложены: таблица `devices` под identity keys,
`messages.body` как контейнер для шифротекста, независимость порядка
событий от содержимого.

---

## 6. Что не заменяет этот план

Перечисленные меры — инженерная гигиена. Они **не заменяют** внешний
пентест и аудит кода независимой стороной. Отчёт по безопасности,
подготовленный в рамках Этапа 7, будет содержать результаты самопроверки по
этому чек-листу, и это должно быть указано в нём явно.
