# Модель синхронизации Mango Messenger

Документ описывает, как данные движутся между устройством и сервером, и
почему именно так. Это основной справочник при реализации Этапов 4–6.

Связанные решения: [ADR-0003](../adr/0003-room-as-single-source-of-truth.md),
[ADR-0004](../adr/0004-outbox-and-idempotency.md),
[ADR-0005](../adr/0005-conflict-resolution.md),
[ADR-0006](../adr/0006-websocket-is-not-the-only-channel.md).

---

## 1. Основной принцип

Room — единственный источник истины для интерфейса. Экран **никогда** не
подписан на сеть.

```
                 ┌──────────────────────────────┐
  WebSocket ───► │                              │
  REST /sync ──► │             Room             │ ──► Repository ──► ViewModel ──► UI
  REST ответы ─► │  (единственный источник       │
                 │   истины для интерфейса)     │
                 └──────────────┬───────────────┘
                                ▲
          локальная запись      │      чтение очереди
                 ┌──────────────┴───────────────┐
                 │      outbox_operations       │ ──► OutboxProcessor ──► сервер
                 └──────────────────────────────┘
```

Следствие: офлайн и онлайн неразличимы для кода экрана. Отличается только
индикатор состояния записи.

## 2. Запись: путь операции

### 2.1. Постановка в очередь

```
UI intent
  │
  ├─ 1. clientOpId = UUIDv7()            ← генерируется ДО запроса
  │
  ├─ 2. ┌─ ОДНА ТРАНЗАКЦИЯ ────────────────────────────────┐
  │     │  оптимистичная запись в Room (syncStatus=PENDING) │
  │     │  вставка в outbox_operations                      │
  │     └───────────────────────────────────────────────────┘
  │
  └─ 3. возврат Outcome.Success → интерфейс уже обновлён
```

Транзакция обязательна. Без неё возможны два испорченных состояния:
сообщение видно, но никогда не уедет; либо операция есть, а сообщения в
интерфейсе нет.

Метод репозитория возвращает успех, если изменение **сохранено локально**.
Доставка — отдельный асинхронный процесс.

### 2.2. Обработка очереди

```
OutboxProcessor (WorkManager + триггер по появлению сети)
  │
  ├─ выбрать пачку: status=PENDING AND next_attempt_at <= now
  │                 AND зависимость уже выполнена
  │                 ORDER BY created_at          ← порядок действий пользователя
  │
  ├─ пометить IN_FLIGHT
  │
  ├─ POST/PATCH с заголовком Idempotency-Key: clientOpId
  │
  ├─ 2xx  → применить ответ сервера к Room, удалить операцию,
  │          продвинуть курсор — одной транзакцией
  │
  ├─ 4xx  → status=FAILED, показать пользователю.
  │          Автоповтора нет: повтор не изменит результат
  │
  └─ 5xx / сеть / таймаут
           → attempt_count++, next_attempt_at = now + backoff
```

### 2.3. Backoff

Экспоненциальный с **полным джиттером**:

```
delay = random(base, min(base * 2^attempt, max))
base = 1 c,  max = 5 мин
```

Джиттер обязателен. Без него все устройства, потерявшие сеть одновременно,
вернутся к серверу одной волной — ровно в тот момент, когда он
восстанавливается.

Ограничение числа попыток различается по типу ошибки:

| Ошибка | Повторы |
|---|---|
| Сеть, таймаут | неограниченно — пользователь мог быть офлайн сутками |
| 5xx | до 8 попыток |
| 429 | по `Retry-After` сервера, он приоритетнее формулы |
| 401 | повтор после успешного обновления токена |
| 4xx прочие | не повторяется |

Реализовано в `RetryPolicy` (`:core:common`), покрыто 10 тестами.

### 2.4. Зависимые операции

Комментарий к задаче не должен уехать раньше самой задачи. Операция может
указывать `depends_on_op_id`; до выполнения зависимости она имеет статус
`BLOCKED` и не выбирается в пачку.

Инвариант «есть зависимость → статус BLOCKED» задаётся в одном месте
(`outboxOperation(...)`). Это сделано после ошибки, когда дублирование
конструктора операции в двух репозиториях привело к расхождению — тест
`status change patch depends on task creation while unsynced` её поймал.

### 2.5. Схлопывание операций

Для черновиков предыдущая операция по той же сущности удаляется при
постановке новой: промежуточные состояния черновика никому не нужны, а
быстрый набор текста иначе забивает очередь.

## 3. Восстановление после перезапуска

Очередь персистентна, поэтому переживает принудительное закрытие приложения.
При старте процесса (`MangoApplication.onCreate`) выполняется:

1. `IN_FLIGHT → PENDING` — процесс был убит в момент отправки, и неизвестно,
   дошёл ли запрос. Повтор безопасен благодаря `Idempotency-Key`.
2. Разблокировка операций, чьи зависимости уже выполнены.

Проверено тестом `queue survives process restart and in flight work is recovered`.

## 4. Чтение сообщений: серверный порядок

### 4.1. Порядок

Истина — `messages.seq`, монотонный **внутри чата**. Клиент не придумывает
порядок.

- Подтверждённое сообщение: `seq` задан.
- Локальное неподтверждённое: `seq = NULL`, сортируется в хвост по
  `created_at`.

Запрос выборки: `ORDER BY (seq IS NULL) DESC, seq DESC, created_at DESC`.
Список рисуется реверсивно, поэтому неотправленное сообщение визуально
оказывается внизу переписки — там, где пользователь его и ожидает.

### 4.2. Дедупликация

Три независимых рубежа:

1. Уникальный индекс `(conversation_id, client_msg_id)` в Room.
2. Уникальный индекс `(conversation_id, sender_id, client_msg_id)` в PostgreSQL.
3. `Idempotency-Key` на уровне HTTP.

Подтверждение сервером сопоставляется по `client_msg_id`, а не по id, поэтому
повторный ответ на ту же операцию обновляет ту же строку
(тест `confirming the same operation twice is idempotent`).

### 4.3. Разрывы истории

Клиент хранит разрывы явно: `message_gaps(conversation_id, from_seq, to_seq)`.
При скролле в разрыв догружается именно пропущенный диапазон.

Запись пачки и закрытие разрыва выполняются **одной транзакцией**, причём
порядок выбран сознательно: если упасть после записи сообщений, но до
удаления разрыва, диапазон просто загрузится ещё раз (операция идемпотентна).
Обратный порядок был бы опасен — разрыв закрыт, а сообщений нет.

Пагинация — Paging 3 + `RemoteMediator`, окна по `seq`, без `OFFSET`.

## 5. Догонка пропущенных событий

```
клиент помнит: lastEventId (GLOBAL) + per-conversation seq

WS connect
   │
   ├─ AUTH (токен в первом кадре, не в URL)
   │
   ├─ ◄── SERVER_HELLO{lastEventId}
   │
   ├─ serverLastEventId > localLastEventId ?
   │        │
   │        ├─ да → GET /v1/sync?since=<local>&limit=500, постранично
   │        │        применять события и продвигать курсор ТРАНЗАКЦИОННО
   │        │
   │        └─ нет → просто слушать поток
   │
   └─ ◄── EVENT{id, type, payload} ...
            разрыв в нумерации id → инициировать /sync не дожидаясь реконнекта
```

Курсор хранится **в Room**, а не в DataStore, чтобы продвигаться в одной
транзакции с применением событий. Иначе возможен разрыв: курсор продвинулся,
события не записались — и они потеряны навсегда.

Курсор **никогда не уменьшается** (тест `cursor never moves backwards`):
запоздавшее событие с меньшим id не должно вызывать повторную обработку.

### Полный сброс области

Если курсор устарел настолько, что журнал усечён, сервер отвечает
`RESET_REQUIRED{scope}`. Клиент перезагружает **только эту область** —
конкретный чат или задачи. Полная перезаливка базы при каждом подключении
прямо запрещена требованиями.

## 6. Разрешение конфликтов задач

Полное обоснование — [ADR-0005](../adr/0005-conflict-resolution.md).

### 6.1. Стратегия по полям

| Поле | Стратегия |
|---|---|
| `title`, `description` | LWW по полю |
| `status` | LWW по полю; при равных метках больший `conflictWeight` |
| `priority`, `due_at` | LWW по полю |
| `assignees` | OR-Set: add и remove независимы |
| `comments`, `attachments` | append-only, дедуп по `client_op_id` |
| `subtasks` | append-only + LWW по каждой |

Веса статусов: `DONE(4) > CANCELLED(3) > REVIEW(2) > IN_PROGRESS(1) > TODO(0)`.
Завершение — более сильное намерение, чем возврат в работу.

### 6.2. Протокол

Клиент отправляет `PATCH /v1/tasks/{id}`:

```json
{
  "baseVersion": 7,
  "changedFields": { "status": "DONE" },
  "fieldTimestamps": { "status": 1731412500000 }
}
```

Сервер:

| Условие | Действие |
|---|---|
| `baseVersion == version` | применить, `version++`, записать в `task_events` |
| `baseVersion < version` | применить per-field LWW, вернуть `200` с объектом и `conflicts: ["status"]` |

Клиент всегда принимает серверный объект как истину. Если его правка
проиграла — показывает ненавязчивое уведомление «изменено на другом
устройстве», а не диалог выбора: выбирать пользователю не из чего, решение
уже принято детерминированным правилом.

### 6.3. Почему это безопасно

Каждое изменение пишется в `task_events` вместе с актором, полем, старым и
новым значением. Даже проигравшая правка остаётся в истории — конфликт
всегда можно разобрать постфактум. Это и есть страховка от молчаливой
потери данных.

## 7. Связь задачи с исходным сообщением

При создании задачи из сообщения сохраняются:

- `source_message_id` — ссылка для перехода;
- `source_sender_name`, `source_message_snapshot`, `source_created_at` —
  **снапшот на момент создания**.

При удалении сообщения задача помечается `source_unavailable = true`.
**Снапшот не стирается**: иначе задача теряет контекст и становится
бессмысленной. Переход к сообщению блокируется, текст остаётся видимым.

Проверено тестом `deleting the source message keeps the task readable`.

## 8. Состояния записи в интерфейсе

| `SyncStatus` | Значение | Как показывается |
|---|---|---|
| `SYNCED` | подтверждено сервером | без индикатора |
| `PENDING` | ждёт отправки | часы |
| `IN_FLIGHT` | отправляется | круговой прогресс |
| `FAILED` | сервер отклонил | красный значок + действие «повторить» |

`FAILED` **не** переотправляется автоматически — это решение пользователя
(тест `failed operations are excluded from automatic retries`).
